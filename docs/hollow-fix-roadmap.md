## 세션 프로토콜 — "다음 작업 진행해줘"

사용자가 **"다음 작업 진행해줘"** (또는 "다음 거", "계속 진행" 등 유사 문구)라고만 입력하면, 아래를 그대로 수행한다. 추가 질문 없이 시작하되, 작업 카드에 🅓(결정 필요) 표시가 있으면 **착수 전에** 카드에 적힌 선택지를 사용자에게 물어본다.

### 0. 작업 선택
- 이 문서의 **작업 순서표**에서 상태가 `⬜`인 **가장 위** 작업을 연다.
- 직전 세션이 남긴 `🔶 진행중`이 있으면 그 작업을 먼저 마저 끝낸다 (카드의 '진행 기록' 참고).
- 사용자가 특정 작업을 지목하면("T09 해줘") 그 작업을 우선한다.

### 1. 사전 검증 — **설계를 믿지 마라**
- 작업 카드의 **전제** 목록을 하나씩 실제 코드로 재확인한다.
  - 줄번호는 밀렸을 수 있다 — 반드시 **인용된 코드 문자열로 Grep**해서 현재 위치를 다시 찾는다.
  - 이 로드맵의 설계는 감사(1차) + 재검증(2차)을 거쳤지만, **그 사이의 커밋으로 무효화됐을 수 있다.**
- 전제가 하나라도 깨졌으면: **구현하지 말고 멈춘다** → 깨진 전제와 수정된 설계를 카드의 '검증 노트'에 기록 → 수정된 설계로 진행. 문제 자체가 사라졌으면 상태를 `⊘ 무효`로 바꾸고 다음 작업으로 넘어간다.
- 전제 확인 중 카드에 없는 새 사실(더 나쁜 동작, 인접 버그)을 발견하면 카드에 기록하고 설계에 반영한다.

### 2. 구현
- 카드의 '설계'와 '구현 가이드'대로 작업한다. 단, 가이드는 지도이지 명령이 아니다 — 실제 코드가 가이드와 다르면 **코드가 우선**이고, 차이를 '검증 노트'에 남긴다.
- CLAUDE.md 개발 지침 준수: 기존 패턴 먼저 읽기, `safeDbOperation` 래퍼, 매칭 시스템 5대 불변조건(App.jsx 11-42), hybrid 시스템/사용자 path 분리(무한 트리거 루프 금지).
- 카드에 '건드리지 말 것'이 있으면 그 코드는 수정 금지.

### 3. 사후 검증
- **구문 체크(필수)**: `npx --yes esbuild App.jsx --loader:.jsx=jsx --jsx=automatic --outfile=/dev/null` → exit 0 확인.
- 카드의 **완료 기준** 체크리스트를 전부 확인한다 (코드 추적으로 시나리오를 손으로 밟아볼 것 — 실행 환경이 없어도 데이터 흐름을 줄 단위로 따라가 확인).
- 수정한 함수를 호출하는 **모든 호출처**를 Grep으로 찾아 회귀 여부를 확인한다.
- 검증에 실패하면 완료 처리하지 않는다. 원인을 고치거나, 막히면 상태 `🔶 진행중` + '진행 기록'에 막힌 지점을 남기고 세션을 마친다.

### 4. 기록
- **App.jsx 헤더 버전 히스토리** 갱신 (버전 +1, 날짜, 변경 내역 — CLAUDE.md 규칙).
- 이 문서: 작업 순서표의 상태 갱신(`✅`/`⊘`) + 카드 '진행 기록'에 1-3줄 (앱 버전, 설계와 달라진 점, 남긴 것).
- `docs/hollow-feature-audit.md` 처리 현황 체크박스 `[x]` 갱신 (해당 감사 항목).

### 5. 커밋/푸시
- 현재 작업 브랜치에 커밋 (메시지: `fix(도메인): 요약 (T-NN)` 형식). 푸시.
- 주요 묶음(Phase 완료 등) 시 main 병합은 CLAUDE.md Git 워크플로를 따른다.

### 세션 운영 원칙
- **한 세션 = 순서표 한 행**이 기본. 카드에 `[묶음가능]` 표시가 있고 세션 여유가 있으면 다음 행까지 이어서 한다.
- 규모 L 작업이 세션 내에 못 끝나면: 컴파일되는 중간 상태로 커밋 + `🔶 진행중` + '진행 기록'에 이어서 할 지점 명시.
- **설계 불신 원칙**: 이 문서의 어떤 설계도 "이미 검증됐으니 그대로 친다"가 아니다. 전제 재확인(1단계) 없이 구현에 들어가는 것 자체가 프로토콜 위반이다.

## Phase 1 — 신뢰 회복: 속이는 화면부터

### T01 · REC-4 — 콘텐츠 필터 실질화 ✅

**전제 (구현 전 Grep으로 재확인)**:

- 🔴 **카드의 파생 공식 `2^gallopMax - 1`은 오산이다.** 갤로핑 probe는 `next = lo + jump`이고 `jump`는 **다음** 라운드용으로만 2배가 된다 → 실제 probe 인덱스는 0,1,3,7,15,31,63,127로, g회에 닿는 최대 인덱스는 `2^(g-1)-1`이다. 따라서 필요한 풀은 **`2^(gallopMax-1)`**이고 g=7이면 정확히 **64** — 즉 **종전 상수가 이미 맞았다**(카드의 "64는 과소" 전제도 틀렸다). 카드 공식(127)을 그대로 썼다면 갤로핑이 평생 닿지 못하는 뒤쪽 절반을 풀에 담아, 카드가 스스로 경계한 '넓지만 닿지 못하는 조합'을 설정이 아니라 코드가 만들어 냈을 것이다(대조군 실측: 풀 127·전부 통과 시 예산 7회를 다 쓰고 lo=63에서 `max` 종료). 올바른 공식이라 **기본값 동작은 무변경**이다.

- **대신 진짜 함정은 프리셋 쪽이었다.** `saveAppSettings`가 suspicionConfig를 **deep merge**(51900)하므로 프리셋 객체에 빠진 키는 **이전 값이 잔류**한다. 그런데 `presetEq`는 프리셋 자신의 키만 비교하므로 화면은 '보수적'로 하이라이트된다 → '보수적인데 점검 길이는 직전 값'인 불일치. 카드가 "presetEq 키 자동 대응"이라 안심시킨 부분이 오히려 위험 지점이었다. 세 프리셋 전부에 새 키를 넣어 해소(대조군 단언으로 고정).
- **`decay`는 읽는 쪽에 하한 가드가 없었다.** 카드가 UI 범위(0.5~0.95)만 지정했는데, 손상된 설정·외부 편집 백업이 0을 넣으면 검증 한 번에 전 작품 의심도가 0이 된다. 읽기 지점에 clamp를 넣되 `Number(null)===0`이라 null 체크를 먼저 해야 했다(안 그러면 '키 없음'이 하한 0.5로 둔갑).

- **`buildTasteKeywordPool`의 두 경로는 weight 스케일이 다르다.** 패턴 경로는 `1 + win_rate`(1.55~2.0)인데 폴백 경로는 **1.2 고정**이다. 카드는 "kw→가중치 시드"라고만 했는데, 그 1.2를 그대로 승률로 넣으면 `scoreWeb`의 `(wr-0.5)*100`에서 **음수→0점**이 되어 폴백이 아무 효과가 없다. 환산이 필수였다: 패턴 경로는 `w-1`로 원래 승률 복원, 폴백 경로는 상수 `WEB_TASTE_FALLBACK_WR = 0.7`(토큰당 20점). 그래서 폴백의 차등은 승률이 아니라 **'일치 개수'**에서 나온다 — 3개 맞으면 60점(초록)이 되는 눈금으로 잡았다.
- **'tasteMap이 비면'을 그대로 쓰면 안 된다.** 정적 메트릭 행이 `sample_size≥3`을 만족한 채 `win_rate=NULL`로 들어오므로 tasteMap은 **비어 있지 않으면서 전 값이 0**인 상태가 흔하다. 판정을 `Object.keys().length === 0`이 아니라 **`some(v => v > 0.5)`**(= scoreWeb이 실제로 점수를 줄 수 있는 값이 하나라도 있는가)로 잡았다.

**설계 (실제 구현)**: ① tasteMap에 쓸 수 있는 승률이 하나도 없을 때만 `buildTasteKeywordPool` 재사용해 시드(mode-aware라 모드 분기 불요, ELO 서재는 진입 자체를 안 함). ② weight→유사 승률 환산(위 검증 노트). ③ `webRecoTasteBasis` state("patterns"|"library"|"none") + 추천 섹션 안내 한 줄 + 정렬 칩 캡션. ④ 전환 슬롯의 낡은 win_rate 이슈는 T33에 기록만.
